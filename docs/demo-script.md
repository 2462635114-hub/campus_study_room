## 1. 演示目标

在 5 分钟内让评委/观众看到一条完整的“**学生预约 → 座位释放 → 管理员管理 → 数据统计**”业务闭环，并说明项目的工程与安全设计，传达“真实开发过程、可运行、可测试、有文档”的项目形象。

4. 工程与安全有真实设计：CSRF、密码哈希、越权防护、SQLite 并发预约方案、pytest 自动化测试（约 30 秒）。

### 3.3 备用方式：手动创建管理员（自动建表）

```powershell
# 交互式输入密码（推荐：密码不会留在命令历史中）
flask create-admin --username admin

# 或非交互式指定密码（便于脚本化；注意命令历史/日志可能泄露密码）
flask create-admin --username admin --password "DemoAdmin#2026"
```

- 命令会**自动创建数据库表**，首次运行也无需先执行 `flask init-db`；
- 不传 `--password` 时会隐藏输入并二次确认；
- 密码要求：至少 8 位、首尾不能有空格、不能过于简单（至少 3 种不同字符）；
- 该方式创建的管理员**不会**被强制改密（仅 `flask seed-demo` 创建的演示 `admin` 带 `must_change_password=True`）。

### 3.4 重置演示数据（谨慎，会丢失本地数据）


> 该操作会清空本地数据库，生成全新示例数据；仓库中的 `instance/*.db` 已被 `.gitignore` 忽略，不会提交。

## 6. 演示话术要点（可直接照读）

1. **定位**：“这是一个教学与竞赛展示项目，所有数据都是示例数据。”
2. **业务闭环**：“学生按时间段找座位并预约，管理员维护资源和处理预约，数据实时进入统计。”
3. **核心规则**：“预约只能约未来 30 天、30 分钟粒度、同座位同用户都不能时间重叠；签到窗口是开始前 15 分钟到开始后 30 分钟。”
4. **并发保护**：“SQLite 没有排他约束，所以我们用写锁事务 + 占位表唯一约束做双层保护，而不是只靠一次 SELECT。”
5. **安全**：“CSRF 全局防护、密码哈希、后端鉴权、同源跳转校验、CSP 响应头。”
6. **诚实边界**：“未实现定时任务、邮件通知、找回密码、第三方登录；没做压力测试和真实用户调研；测试结果为真实运行的 204 passed（连续三次全绿）与冒烟 47/47。”

## 7. 备用方案与异常处理

| 风险 | 处理方式 |
|---|---|
| 签到按钮当场不出现 | 正常现象：按钮仅在签到窗口内显示。改为口述规则，并展示示例数据中的“已签到/已完成”记录；不要伪造签到成功 |
| 首次登录强制改密打断流程 | 提前改密；若现场出现，把它当作“安全特性”展示（约 20 秒）并完成改密后继续 |
| 端口 5000 被占用 | `python run.py` 启动失败时设置 `$env:PORT="5001"` 再启动，访问 `http://127.0.0.1:5001` |
| 数据库未初始化导致首页 500 | 执行 `flask init-db`；已有示例数据可执行 `flask seed-demo`；不要现场删除数据库 |
| 图表不渲染 | 说明本地 Chart.js 加载失败或无数据，页面已降级为数据表格（这是设计好的降级方案），继续讲统计表格 |
| AJAX 刷新失败 | 页面会自动整页刷新；也可直接点“刷新座位状态”按钮 |
| 预约冲突演示不稳定 | 改为口述规则 + 展示“我的预约”列表中的状态记录，不要现场反复尝试 |
| 时间超时 | 优先保留：学生预约闭环、管理端预约/CSV、统计页；压缩技术细节与 Q&A |
| 投影环境无网络 | 项目本身不依赖 CDN，页面与图表均为本地资源，可正常演示 |

## 8. 演示安全提示

1. **不要展示** `.env` 文件、`SECRET_KEY`、数据库文件、真实密码或任何敏感配置；如需展示配置，只展示 `.env.example` 中的键名。
2. 演示密码统一加“演示专用”前缀说明；**禁止**在任何真实系统复用演示密码。
3. 不虚构数据：不得声称真实校园部署、真实用户量、使用成效、性能指标、比赛成绩。
4. 不夸大功能：未实现的功能（定时任务、邮件通知、找回密码、第三方登录、用户管理界面、审计日志界面）明确说“计划中”。
5. 不修改演示数据之外的本地数据；需要重置示例数据时先备份（见 3.3），并说明会清空本地数据库。
6. 讲解测试结果时只使用最近一次真实运行输出，不口述未经验证的“通过数量”。

## 9. 常见提问与参考回答

| 提问 | 参考回答 |
|---|---|
| 为什么选择 SQLite？ | 项目定位是本地教学演示、单机小规模，SQLite 零配置、文件即数据库，便于随项目分发；并发写入用写锁事务 + 唯一约束保证正确性，并记录了未来迁移 PostgreSQL 的演进方向 |
| 如何保证并发下不会重复预约？ | 两层：每个事务 `BEGIN IMMEDIATE` 取得写锁，冲突检查与写入串行化；`reservation_slots` 上的两个唯一约束在数据库层兜底，重复插入会触发 `IntegrityError` 并回滚 |
| 密码怎么存？ | `werkzeug.security.generate_password_hash`（当前为 scrypt，带随机盐），数据库只存哈希；登录用 `check_password_hash` 校验 |
| CSRF 是怎么做的？ | Flask-WTF `CSRFProtect` 全局启用，所有 POST 表单带令牌；令牌失效时统一 flash 提示并安全跳回 |
| 学生能不能访问管理员页面？ | 不能。后端 `admin_required` 装饰器校验角色，学生访问返回 403；隐藏按钮只是展示层 |
| 为什么没有定时任务？ | 第一版用 CLI `flask sweep-reservations` 和管理端按钮手动触发，已列入后续迭代；文档“已知限制”中有说明 |
| 测试全部通过了吗？ | 是的，最终真实结果为 204 passed in 47.61s（连续三次全绿，无 failed/skipped/warning），集成冒烟 47/47 项通过；测试使用临时数据库，未触碰演示数据库 |
| 这个项目有什么不足？ | SQLite 单写锁不适合高并发多机部署；未做压力测试与真实用户调研；无找回密码/邮件通知/第三方登录；管理端统计为演示规模设计；未引入数据库迁移工具；测试与文档仍需持续完善 |
